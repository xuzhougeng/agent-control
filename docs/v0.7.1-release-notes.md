# v0.7.1 版本说明：UI 路由审批闸

发布日期：2026-05-08
GitHub Release: <https://github.com/xuzhougeng/agent-control/releases/tag/v0.7.1>

> v0.7.0 升级说明见 [v0.7.0-release-notes.md](v0.7.0-release-notes.md)。本版本是
> v0.7.0 的增量小迭代，**完全兼容**，无破坏性改动。

## 一句话总结

cc-agent 跑在远程 server 上时，destructive 命令（`rm -rf` / `mkfs` /
`shutdown` / `systemctl stop` / ...）现在会在 **cc-control 的 Web/iOS/Windows
UI 上弹出 Pending Approval 卡片**，运维点 Approve 或 Reject 决定。
不需要 SSH 上服务器、不需要在终端打 `y/n`。

## 现状一览

cc-agent 的审批闸现在有四档（按优先级排序）：

| 模式                       | 触发条件                              | 行为                                          |
|----------------------------|---------------------------------------|-----------------------------------------------|
| `-full-permission`         | flag                                  | yolo，跳过所有审批                            |
| `-deny-destructive`        | flag                                  | 静默拒绝所有 destructive                      |
| `-control-url <url>`       | flag（v0.7.1 新）                      | **路由到 cc-control UI** ← 新增               |
| CLI REPL（无 flag）        | 默认                                  | stderr 提示 `[y/N]`                           |

**典型生产部署**：

```bash
./cc-agent \
  -provider deepseek -model deepseek-chat \
  -cwd /var/log -allowed-roots /var/log \
  -control-url ws://your-control:18180/ws/agent \
  -agent-token <agent-token> \
  -server-id ops-01 \
  -memory /var/lib/cc-agent/sessions.db
```

不再加 `-deny-destructive`。任何 destructive 命令会在 UI 弹审批卡片，5 分钟
内点 Approve 就执行，超时自动拒绝。

## 流程动画（端到端时间线）

```
T+0s    模型决定: bash {command="rm -rf /var/log/old/*"}
T+0s    cc-agent: DangerousReason="recursive rm" → RemoteApprover.Approve
T+0s    cc-agent → cc-control: approval_request{request_id, command, reason}
T+0s    cc-control: 创建 approval_needed SessionEvent + audit log
T+0s    cc-control → 所有附着的 UI 客户端: chat_msg + Pending Approval 卡片
        UI 显示:
          ┌─ Pending Approvals  1 ──────────────┐
          │ 8536aa5c @ ops-01                   │
          │ instance ad4aef30                   │
          │ ┌─────────────────────────────────┐ │
          │ │ [recursive rm] rm -rf /var/log/...│
          │ └─────────────────────────────────┘ │
          │ [ Approve ]  [ Reject ]             │
          └─────────────────────────────────────┘
T+12s   运维点 Approve
T+12s   UI → cc-control: action{kind:"approve", event_id}
T+12s   cc-control: 检测 AgentRequestID → 调 SendApprovalDecision
T+12s   cc-control → cc-agent: approval_decision{request_id, approved=true}
T+12s   cc-agent: RemoteApprover.dispatch → bash 解除阻塞
T+13s   bash 实际执行 rm -rf
T+13s   tool 返回结果，模型继续 ReAct
T+18s   chat_out final → UI 渲染最终回答
```

## 协议变更（向后兼容）

新增两条 WS 消息（agent ↔ control）：

| 方向            | 类型                  | 字段                                        |
|-----------------|-----------------------|---------------------------------------------|
| agent → control | `approval_request`    | `request_id`, `command`, `reason`, `ttl_ms` |
| control → agent | `approval_decision`   | `request_id`, `approved`, `actor`           |

`SessionEvent` 新增 `agent_request_id` 字段（omitempty），用来区分 PTY 和
cc-agent 的审批：

- 字段为空 → 旧 PTY 路径（操作员的 approve/reject 转成 `y\n` / `n\n`
  写入 PTY，跟 v0.6 一样）
- 字段非空 → 新 cc-agent 路径（操作员的 approve/reject 转成
  `approval_decision` 发回 agent）

旧 cc-proxy + cc-control v0.7.1 / cc-web v0.7.1 完全兼容；新 cc-agent
只跟 v0.7.1+ 的 cc-control 协议一致。

## 同时改进的细节

1. **Dangerous regex 加紧**：原本 `rm a.tmp b.tmp` (无 `-rf`) 不会触发审批，
   现在也会拦下来。修补的是实测发现的 bypass 路径——模型被 deny 后会自然降级
   到 plain `rm`。
2. **诊断日志**：cc-agent 和 cc-control 在 approval 路径上都加了 slog.Info
   关键步骤，方便排查"approve 点了但没反应"这类问题。
3. **错误时自然降级**：approver 超时或拒绝时，bash 工具返回
   `DENIED by operator (reason: <X>)` 字符串作为工具结果（不抛错），让模型
   自己选安全方案。

## 升级指南

### 已有 v0.7.0 部署

完全兼容升级。三步：

```bash
# 1. 拉新二进制
wget -O /usr/local/bin/cc-agent.new https://github.com/xuzhougeng/agent-control/releases/download/v0.7.1/cc-agent-linux-amd64
wget -O /usr/local/bin/cc-control.new https://github.com/xuzhougeng/agent-control/releases/download/v0.7.1/cc-control-linux-amd64
chmod +x /usr/local/bin/{cc-agent,cc-control}.new

# 2. 替换 + 重启 cc-control（先重启控制面）
sudo systemctl stop cc-control
mv /usr/local/bin/cc-control.new /usr/local/bin/cc-control
sudo systemctl start cc-control

# 3. 替换 + 重启 cc-agent（每个节点）
sudo systemctl stop cc-agent
mv /usr/local/bin/cc-agent.new /usr/local/bin/cc-agent
# 如果之前用 -deny-destructive，可以去掉这个 flag 启用 UI 审批
sudo systemctl start cc-agent
```

cc-web 静态资源也需要更新（如果不用 cc-control 内置的）。

### 仍想保持自动拒绝

依然保留 `-deny-destructive`，行为完全跟 v0.7.0 一致。

### 想全自动通过

`-full-permission`，仅限受信脚本环境。

## 已知 caveat

- 审批超时是 **固定 5 分钟**。还没暴露成 flag。运维如果在睡觉、agent 又 await
  approval，bash 工具会在 5 分钟时拒绝。模型通常会试着用更安全的命令再来一次。
- 同一个 chat session **同一时刻只能有一个待审批**。这是协议层面的硬约束（cc-control
  以 session 为单位 awaiting，第二个 approval_request 会被静默丢弃）。
- 浏览器对 ES module 缓存比较激进；升级 cc-web 后如果 UI 没出现 Approve/Reject
  按钮，做一次 hard reload (`Ctrl+Shift+R`) 即可。
- iOS / Windows native 客户端默认还没渲染 Approve/Reject 按钮（v0.7.1 只改了
  cc-web）。要在三端 UI 上点按钮的支持，等 v0.7.2。

## 测试覆盖

- 协议层 3 个 unit test（`internal/transport/control/client_test.go`）：
  - `TestRemoteApprover_DispatchUnblocksApprove`：approve / reject 各一遍
  - `TestRemoteApprover_TimeoutDenies`：5 分钟无响应 → 拒绝
  - `TestRemoteApprover_NoSessionInContextRejects`：缺少 WithSession 时报错
- Dangerous regex 5 个新 case（`internal/tools/approval_test.go`）
- 真实端到端：Playwright 驱动 → DeepSeek → cc-agent → cc-control →
  UI 点 Approve → cc-agent → bash 执行（实测 timeline 在上面"流程动画"节）
